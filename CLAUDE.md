# CLAUDE.md — New England Ski Resort Guide

Project rules for Claude Code. Read this before any task in this repo.

## What this is

A **public**, static website cataloguing New England ski areas roughly Pats Peak size and up
(~650 ft vertical minimum). Static facts + original editorial per resort, live weather, and
automatically fetched snow reports.

## Non-negotiable constraints

- **No framework, no bundler, no build step for the site itself.** Vanilla HTML + CSS + ES
  modules. `index.html` must work when opened from `file://` or any static host.
- **Node is used only for tooling** (`tools/`), never at runtime for visitors.
- **No runtime dependency on any server.** The deployed site is static files only.
- **The data is the product.** Presentation code never hardcodes resort facts. If you find
  yourself typing a resort name into a `.js` or `.html` file, stop — it belongs in JSON.

## Data rules — the important ones

1. **One JSON file per resort**, named `<slug>.json`, slug is lowercase-hyphenated
   (`mad-river-glen`, `mount-snow`, `black-mountain-nh`).
2. **Never invent a number.** Every factual field group carries a `source` URL and a
   `verifiedOn` ISO date. If a figure cannot be sourced, use `null` and add the field to
   `data/UNVERIFIED.md` — do not guess, do not interpolate, do not carry a number over
   from a similar resort.
3. Prefer the **resort's own website** for stats, then Ski<State> associations, then
   OnTheSnow/ZRankings. Record which was used.
4. **Editorial fields are opinions and must read like it** — specific, concrete, and
   willing to say a mountain is icy, crowded, or overpriced. Generic marketing prose is a
   bug. Never copy sentences from a resort's marketing site or from any review site.
5. After editing any file in `data/resorts/`, run `node tools/build-index.mjs` and
   `node tools/validate.mjs`.

## Snow fetcher rules

- User-Agent must identify the project and a contact URL.
- Honor `robots.txt`. Minimum 2 hours between requests to the same host. Never parallel-hit
  one host.
- Try in order: official JSON endpoint → static HTML parse (cheerio) → Playwright. Stop at
  the first that works and record which tier was used.
- Store **numbers and short condition labels only**. Never store or display prose copied
  from a resort's report.
- Every adapter must fail soft: return `{status:'error', reason}` rather than throwing, and
  the UI falls back to a link to the official report.
- Every displayed report shows a relative "as of" timestamp and a source link.

## The `private/` boundary — do not blur this

`private/` holds personal-use material (downloaded trail maps) and is gitignored. It is
never committed, never deployed, never referenced from any file under `data/` or `assets/`,
and no page the public can load may link to a path inside it.

The public site links to resorts' **official** trail map URLs via `links.trailMap`. If you
ever find yourself pointing a resort JSON field at `private/`, that is a bug.

## Style

- ES modules, `const`/`let`, no jQuery, no CDN scripts except Leaflet on the map page.
- CSS custom properties for color; support light and dark via `prefers-color-scheme`.
- Mobile-first. The comparison table must scroll horizontally inside its own container —
  the page body must never scroll sideways.
- Semantic HTML and real `<a href>`s so the site is crawlable and linkable.
- Accessible: keyboard-navigable filters, visible focus, WCAG AA contrast.

## Working style for this repo

- Work in **small batches**. When filling resort data, do **4–5 resorts per task**, then stop
  and report. Do not attempt 30 resorts in one pass.
- Research before writing. Cite as you go; do not backfill sources afterward.
- After each batch, run `node tools/validate.mjs` and report anything unverified.
